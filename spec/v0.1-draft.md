# ASCII Wireframes Specification v0.1 (DRAFT)

**Status**: Early Draft
**Last Updated**: 2025-10-26

## Abstract

This document defines ASCII wireframes as a human-readable, plain-text format for communicating user interface designs to AI coding assistants and human developers.

## Goals

- Provide a consistent, unambiguous way to describe UI layouts
- Enable rapid iteration on interface design
- Work seamlessly with version control systems
- Be easy to write without special tools
- Be immediately understandable by both humans and AI

## Core Concepts

### 1. Box Drawing

ASCII wireframes use box-drawing characters to represent visual boundaries and structure.

**Box-drawing characters**:
- `┌ ┐ └ ┘` - corners
- `─ │` - horizontal and vertical lines
- `├ ┤ ┬ ┴ ┼` - connections


```wireframe-src
┌─────────────────────┐
│ Header              │
├─────────────────────┤
│ ┌─────┐  ┌─────┐   │
│ │ Box │  │ Box │   │
│ └─────┘  └─────┘   │
└─────────────────────┘
```


### 2. Interactive Elements

Common UI components are represented with brackets and symbols.


```wireframe-src
[ Submit ]  [ Cancel ]

[____________]

[ Enter text...    ]

┌───────────────┐
│_______________│
│_______________│
└───────────────┘

[ ] Unchecked    [x] Checked

( ) Unselected   (•) Selected

[ Select...  ▾ ]

→ Learn More  or  Learn More →

[🔍] [≡] [⚙]
```


### 3. Lists

Represent collections of items using bullet points.


```wireframe-src
- Item 1
- Item 2
- Item 3
```


### 4. Text Hierarchy

Use spacing and formatting to indicate importance.


```wireframe-src
# Large Heading

## Medium Heading

Regular body text

[Primary Action]  [Secondary Action]
```


### 5. Layout and Spacing

Indentation indicates hierarchy and grouping.


```wireframe-src
┌─────────────────────────────┐
│ App                         │
├─────────────────────────────┤
│                             │
│  Main Content Area          │
│                             │
│  ┌──────────────────────┐   │
│  │ Nested Component     │   │
│  │                      │   │
│  │  Further nested      │   │
│  └──────────────────────┘   │
│                             │
└─────────────────────────────┘
```

## Annotations

Use comments to provide additional context:

```wireframe-src
┌─────────────────────────────────────┐
│ Dashboard                      [≡]  │
├─────────────────────────────────────┤
│                                     │
│  // User profile section            │
│  ┌──────────────────────────────┐   │
│  │ @username             [Edit] │   │
│  └──────────────────────────────┘   │
│                                     │
└─────────────────────────────────────┘
```

## Best Practices

1. **Be Consistent**: Use the same characters for the same elements throughout
2. **Add Context**: Include labels and annotations where helpful
3. **Show State**: Indicate interactive states (selected, disabled, etc.)
4. **Keep it Simple**: Focus on structure over pixel-perfect representation
5. **Consider Responsive**: Note breakpoints or layout variations when relevant

## Known Limitations

**v0.1 focuses exclusively on Tier 1 critical elements.** The following are intentionally not supported in this version:

### Not Supported (Deferred to Future Versions)
- **Layout Patterns**: Card grids, sidebar layouts, navigation bars
- **Advanced Components**: Tables, tabs, modals, tooltips, badges
- **Complex Nesting**: Side-by-side boxes (horizontal layouts)
- **Special Characters**: Divider characters (`┬`, `┴`, `┼`) for complex layouts
- **State Visualization**: Loading states, error states, disabled states
- **Data Visualization**: Charts, graphs, diagrams

### Transformation Limitations
The transformer (v0.1) has the following known limitations:
- **Horizontal layouts** with multiple boxes side-by-side are parsed as nested content containers
- **Navigation headers** with icons and inputs may not preserve exact layout
- **Complex forms** with multiple columns transform but may not maintain alignment
- **Nested interactive elements** (buttons inside boxes inside boxes) work with limited styling

### Workarounds
For unsupported layouts:
- **Card grids**: Use vertical stacking instead of horizontal
- **Sidebars**: Describe in annotations rather than visual layout
- **Tables**: Use lists or describe data structure in comments
- **Complex navigation**: Simplify to basic header with buttons/links

These limitations are intentional to keep v0.1 focused and simple. Future versions may expand based on real-world usage feedback.
